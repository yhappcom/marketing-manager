## Latest validated addition — 114
Canonical principle: **Release notes are version-specific trust metadata, and their marketing latitude is platform-specific. Do not syndicate one public changelog template across Apple and Google Play.**

Apple's current product-page guidance says What’s New appears on the product page and Updates tab, recommends communicating features/fixes based on feedback, ordering changes by importance, and permits CTA language that gets users excited about the update. Google Play's current release guidance is materially stricter: release notes should inform users about recent updates and must not be used for promotional purposes or to solicit user actions. Google supports localized release notes up to 500 Unicode characters per language and exposes release-level installs, updates, performance issues and ratings for comparison, but those metrics do not establish causal impact from release-note wording.

AF0–AF5 governs version-communication evidence. AF0 is false/policy-incompatible version messaging. AF1 is generic changelog noise. AF2 is factual but unmanaged. AF3 requires shipping-version parity, specialist-consequence ordering, safe description of fixed failures, separate Apple/Google rendering, intentional locale maintenance, no overstatement of partial behavior, and an owner for each material claim. AF4 closes the loop to affected-job/support/quality/useful-return evidence without inventing copy causality. AF5 is a reusable cross-app changelog system.

For MintTap, release-note priority follows investor tracking consequence: record/persistence and calculation fixes, reverse-split/cost-basis behavior, ROC/tax-adjustment behavior, distribution/exchange-rate corrections, then lower-impact changes. Market events themselves are not software release deltas. For LogMate, record integrity, totals, backup/restore/offline/sync and import behavior outrank cosmetic changes.
