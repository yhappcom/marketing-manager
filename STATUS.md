## Latest validated addition — 163
The Store-linked developer website is not merely a marketing landing page. For an ad-supported app it is simultaneously support/trust infrastructure and part of the app-ads.txt ownership/authorization chain. Apple requires a localizable Support URL leading to real support/contact information and separately exposes a Marketing URL; Google Play requires a support email and can expose website/phone through Store listing contact details.

AdMob uses the developer website in the public Store listing to derive the host it crawls for `/app-ads.txt`. Google Play apps must put that website in Store listing contact details; for Apple, AdMob instructs developers to use the App Store Marketing URL. The full app-ads.txt URL should not be placed in the Store listing. Crawler host/subdomain/redirect rules matter, and Store metadata changes are not instantaneous: Google documents up to 24 hours for Play website changes to be detected and up to 24 hours for AdMob crawl/verification; Google Ad Manager documents up to 7 days for Apple App Store developer-website changes to be detected.

CA0–CA5: `live Store identity → support integrity → domain/control integrity → app-ads.txt path/content integrity → platform verification → separate support/ad-revenue outcome`. Preserve `website present ≠ support usable ≠ app-ads.txt reachable ≠ app-ads.txt verified ≠ fill/impression/revenue healthy`. Domain/Store-website changes are infrastructure changes, not harmless metadata edits.

For MintTap, reconcile the live iOS Marketing URL + Support URL, Android Store website + support email, effective hostname, root app-ads.txt and AdMob verification before adding more promotional surfaces. This does not alter the Home-ad-free decision: supply authorization and placement aggressiveness are separate concerns. For LogMate, establish and validate this chain before monetized launch rather than at release time.

## Progress interpretation
Zero-cost success is not clicks, followers, karma, pre-registrations, pre-orders or installs. A Store surface, Store asset, support URL or developer website is not usable merely because the platform exposes it. Eligibility, truthful classification, release truth, localization truth, support reachability, domain control and destination-channel permission precede distribution. For ad-supported apps, Store-linked web identity also participates in app-ads.txt authorization; browser reachability, crawler verification and actual monetization are separate evidence states. Prelaunch Store commitment captures intent but does not create demand or prove launch-day use. Native attribution improves observability but does not establish incrementality. Sparse or threshold-suppressed evidence remains inconclusive. Accessibility is a product capability first and a discovery/trust surface second. Platform approval, featuring, recommendations, native marketing assets, Google-owned promotion, AI copy, accessibility labels/tags, category membership, event engagement, localized metadata, prelaunch commitment, app-ads.txt verification or tagged-link conversion are distribution/context/infrastructure signals—not proof of demand, domain correctness, regulatory authority, product-market fit or incremental revenue. Sustainable growth requires qualified users to reach and repeat the promised core value while advertising adds reconciled incremental revenue only from natural states that do not materially degrade that value.
