# 048 — Specialist Localization Semantics for Narrow Professional Apps

Updated: 2026-09-16

## Research question

How should MintTap, LogMate, and future narrow professional apps localize Store/product marketing when literal translation can preserve dictionary meaning but destroy specialist recognition, trust, search intent, or legal/tax meaning?

## Core conclusion

Localization for specialist apps is not `source copy → translated copy`. It is a controlled semantic mapping:

`verified product capability → specialist job/problem → market-specific professional vocabulary → platform metadata surface → proof asset → validation`

The unit to preserve is the **user's domain meaning and decision**, not the source-language wording.

Company rule: **Meaning Before Wording**.

A localized term/copy is acceptable only when it preserves all material dimensions relevant to the claim:

1. domain referent — the same underlying concept;
2. professional convention — terminology actual practitioners/investors use in that market;
3. scope — no broader/narrower capability than implemented;
4. jurisdiction — tax/regulatory meaning is not silently transferred across countries;
5. user intent — the copy still matches the problem the user is trying to solve;
6. proof — screenshots/product state actually substantiate the localized claim.

## Platform facts that change strategy

### Apple

Apple permits localized App Store metadata and localized screenshots/app previews. Localized keywords affect search in countries/regions where that localization is supported. If no localization matches the customer's language, Apple uses another relevant localization or the primary language. Display language can therefore depend on storefront, device language, available localizations, and primary language.

Operational consequence: a localization is a **search + persuasion surface**, not merely a translation layer. A Korean or Japanese keyword set should be researched independently rather than generated by translating an English keyword list.

Apple also allows localized screenshots. Therefore text localization without proof-asset localization is incomplete when screenshot labels/callouts carry specialist terminology.

### Google Play

Google Play supports publisher-supplied translated listing text and localized graphic assets. If publisher translation is absent, users may see automated translation of the default listing. Google explicitly notes native-speaker translation is preferable. Country/region differentiation is separate from language localization and can use Custom Store Listings (CSLs).

CSLs are especially important for professional apps because **same language does not imply same professional context**. Google documents country-targeted listings that can show different feature emphasis to English speakers in different countries. CSLs are not automatically translated; publishers must add their translations.

Operational consequence: distinguish:

- `language localization` — vocabulary/readability/search language;
- `market localization` — different problem emphasis, evidence, tax/regulatory context, workflow convention;
- `product localization` — actual UI/data/behavior changes required for that market.

Do not use language translation as a substitute for missing product localization.

## Specialist semantic classes

Every material Store/community/web term should be classified before localization.

### S1 — Stable product/UI concept

Examples: portfolio, transaction import, dashboard, backup.

Can usually be localized conventionally, but must match actual UI terminology.

### S2 — Domain term with practitioner convention

MintTap examples: distribution, distribution per share, cost basis, reverse split, return of capital (ROC).

LogMate examples: PIC, SIC, block time, flight time, night, instrument, approach, landing.

Do not force expansion/translation where the target profession conventionally uses the English abbreviation. Search vocabulary and UI vocabulary may legitimately differ, but the relationship must be explicit.

### S3 — Jurisdiction-sensitive financial/tax/regulatory term

Examples: withholding tax, ROC tax treatment, tax refund/additional settlement; authority-specific logbook requirements.

Highest semantic risk. A U.S. tax term can describe an instrument/event while the user's local tax consequence differs. Marketing must separate:

`instrument/distribution classification` from `investor-jurisdiction tax treatment`.

For aviation, separate:

`generic logging capability` from `authority/operator compliance claim`.

Never localize a jurisdiction-specific claim by swapping country names or translating terminology.

### S4 — Search-language synonym

A phrase users type even when professionals use another label in-product. It can be useful in keywords/content discovery but should not automatically replace the canonical product term.

### S5 — Claim/risk language

Examples: accurate, automatic, tax-ready, compliant, official, real-time.

These are not translation problems. They are evidence problems. Each locale inherits the same claim-evidence requirement, and some markets can make the claim materially stronger or weaker because of regulatory meaning.

## Semantic localization workflow

For each target market:

1. **Freeze capability truth** — identify exactly what the released product does.
2. **Define the specialist job** — what decision/problem the user recognizes.
3. **Build a term ledger** — canonical concept, target-market practitioner term, common search variants, prohibited/misleading variants, jurisdiction notes.
4. **Map surface role** — Store name/subtitle/keywords/description, screenshots, web article, community answer, in-app UI.
5. **Localize proof** — ensure screenshot/UI state and terminology agree.
6. **Native-domain review** — prioritize a target-market practitioner/domain reviewer over generic linguistic fluency for S2/S3 terms.
7. **Behavioral validation** — observe qualified search impressions, Store conversion, first value, support confusion, and community corrections. Do not judge localization by linguistic preference alone.
8. **Version the mapping** — terminology changes are evidence-bearing product/marketing changes, not disposable copy edits.

## MintTap application

MintTap should not position localization as simply English↔Korean translation. At minimum the ledger must distinguish:

- YieldMax/product brand and ticker terms that remain unchanged;
- `distribution` versus ordinary `dividend` where product/tax meaning differs;
- `return of capital (ROC)` as a distribution/tax classification versus the Korean investor's subsequent local tax handling;
- reverse split terminology and ratio notation;
- cost basis / principal recovery / total return, which can be conflated if translated casually;
- withholding at distribution versus later refund/additional-tax settlement.

Store proof should show the market-specific hard case only if the released product actually handles it. A Korean Store route may legitimately emphasize exchange rate and local settlement workflow while an English/U.S. route emphasizes distribution/ROC tracking, but these are separate market stories requiring separate proof.

## LogMate application

Pilot vocabulary is unusually resistant to naive translation because English abbreviations are part of operational practice. A localized Korean/Japanese listing may retain PIC/SIC/IFR/Block while translating explanatory copy around them.

Authority claims require a separate evidence layer. `pilot logbook`, `electronic flight log`, and `record PIC/SIC/night/instrument time` are capability statements. `FAA-compliant`, `EASA-compliant`, or authority-specific required-field claims are jurisdictional claims and must not be introduced until verified against the relevant authority and implemented behavior.

Import-source names (CrewConnex, AIMS, NetLine/Crewlink, FLICA, NAVBLUE/RAIDO, etc.) should remain exact identifiers. Marketing should never imply compatibility until the parser/import path is implementation-verified.

## Zero-cost operating model

For narrow apps, full localization into many languages is usually the wrong first move. Use **evidence-gated localization depth**:

`market evidence → terminology ledger → metadata localization → proof localization → product localization if required`

Promote a locale only when there is enough qualified demand or strategic need to maintain terminology, screenshots, support/help content, and claim correctness. Machine translation may be useful for low-risk drafts or coverage, but S2/S3/S5 content requires domain review before it becomes a durable acquisition surface.

## New company rules

### Meaning Before Wording
Preserve domain meaning, scope, jurisdiction and user decision before linguistic similarity.

### Locale Is Not Market
Language localization and country/professional-context localization are separate decisions.

### Proof Travels With the Claim
Localized copy cannot outrun the localized screenshot/product evidence that substantiates it.

### Domain Review Before Scale
For specialist terminology, practitioner/domain validation outranks generic translation polish.

### No Compliance by Translation
Regulatory/tax/compliance claims are re-established per jurisdiction; they are never inherited automatically from another locale.

## Measurement

Do not optimize localization only for Store conversion. The minimum chain is:

`localized qualified impression → product-page engagement → install → first value → useful return`

Track support questions/community corrections as semantic failure signals. A localization that increases installs but causes users to misunderstand tax handling, supported import sources, or logbook compliance is a regression.
