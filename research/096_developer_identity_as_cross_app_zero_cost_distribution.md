# 096 — Developer Identity as Cross-App Zero-Cost Distribution

Validated: 2026-09-18

## Canonical principle

**Build the developer identity as a trust-and-discovery bridge, not as a generic umbrella brand. Cross-app exposure is useful only when the next app is relevant.**

For a company expecting multiple narrow professional apps, developer identity is a durable zero-cost surface that sits above any one launch. It must not become an excuse to cross-promote unrelated products aggressively.

## First-party facts

### Google Play

Google Play supports an optional Developer Profile / developer account page once at least one app is published. Users can visit it to learn about the brand, discover a developer-selected featured app, and see other published apps. Google assigns the page a URL that can be shared externally. Even without a configured profile, other apps remain visible in developer-specific app collections.

Source: Google Play Console Help, “Create or update your Developer Profile.”
https://support.google.com/googleplay/android-developer/answer/9873827

Implication: the company has an owned-within-Play, zero-media-cost portfolio discovery surface. This is not equivalent to guaranteed traffic; it is an available destination and credibility surface.

### Apple App Store

Apple displays the developer name under the app name on product pages and when users install the app. For organization enrollment, a registered trade/DBA name can be selected when the first app is added; Apple states that this developer name cannot later be edited or updated through that process. Individual enrollment uses the legal name.

Source: Apple App Store Connect Help, “Set your developer name.”
https://developer.apple.com/help/app-store-connect/create-an-app-record/set-your-developer-name

Implication: Apple developer identity should be treated as durable infrastructure, not campaign copy. Do not assume it can be rebranded casually after a portfolio grows.

## Portfolio-level marketing model

The correct chain is:

`credible app experience → developer identity recognition → relevant portfolio discovery → qualified second-app visit → independent promise validation → first value → useful return`

The wrong chain is:

`installed one app → push every other company app → more impressions = success`

Niche portfolios often have weak audience overlap. MintTap targets YieldMax investors; LogMate targets pilots. Their coexistence under one developer identity can establish that the developer ships focused utilities, but it does not make a MintTap user a qualified LogMate prospect or vice versa.

## X0–X5 Cross-App Relevance Gate

### X0 — Misleading portfolio transfer
Cross-promotion implies professional relevance, endorsement, shared functionality, regulatory suitability, or audience fit that is not true.

**Action:** prohibited.

### X1 — Generic exposure
Another app is shown merely because it belongs to the same developer, with no demonstrated audience/job overlap.

**Action:** tolerate passive store-level visibility; do not create intrusive in-app promotion.

### X2 — Plausible adjacency
There is a plausible audience or workflow relationship, but no evidence that users actually want the second app.

**Action:** optional low-friction discovery only; no interruption, gating, or repeated prompts.

### X3 — Evidence-backed relevance
A real user/job overlap is documented and the second app’s promise is independently accurate. The route preserves context and does not interfere with the current app’s core task.

**Action:** eligible for deliberate cross-app routing.

### X4 — Qualified cross-app value
Cross-app visitors reach the second app’s first value and useful return without degrading source-app retention/trust.

**Action:** retain and optimize conservatively.

### X5 — Reusable portfolio pattern
Repeated evidence across apps/releases shows that a defined adjacency reliably creates qualified second-app use while preserving trust.

**Action:** encode as a reusable launch/growth playbook.

## Company operating rules

1. **Developer identity is a trust surface first.** Keep naming, iconography/brand system, developer profile copy, website, support and privacy identity consistent enough that users can verify who publishes the app.
2. **Do not force visual sameness between niche apps.** MintTap and LogMate need category-appropriate product identities. Portfolio coherence should signal publisher provenance, not erase specialist context.
3. **Google Developer Profile is portfolio infrastructure.** Audit whether it exists, whether its copy is current, which app is featured, and whether the featured choice reflects company strategy rather than arbitrary recency.
4. **Apple developer name is high-cost identity infrastructure.** Record the exact public developer name and organization/legal relationship before future brand decisions. Do not plan a casual rename workflow.
5. **Passive Store portfolio visibility is not permission for in-app cross-promotion.** Any in-app promotion must pass X3 and the existing interruption/trust gates.
6. **Do not use one specialist audience to bootstrap an unrelated specialist app.** MintTap’s Reddit/blog audience should not become a LogMate distribution list merely because both products share a developer.
7. **Shared corporate channels should publish company-level evidence only when useful.** Product-specific expertise remains in product-native communities and content surfaces.
8. **Every app validates its own promise.** Publisher reputation can reduce uncertainty, but it cannot substantiate tax, investing, aviation, regulatory, privacy, or safety claims.

## Zero-cost launch use for future niche apps

Before a future app launches:

- verify public developer identity on both stores;
- update the Google Developer Profile if the new app materially changes the portfolio story;
- decide whether any existing app has X3 audience/job adjacency;
- if not, rely on passive portfolio discovery and the new app’s own community/store channels;
- if yes, define one low-friction route and measure qualified second-app behavior rather than raw taps;
- keep corporate website/developer profile/support identity synchronized with the shipped portfolio.

This converts previous launches into a small amount of durable trust capital without treating existing users as free ad inventory.

## Measurement contract

Minimum ledger:

`source app/surface → developer-profile or cross-app route → X-class → second-app store visit → install → first value → useful return → source-app retention/trust signal`

Primary decision metric:

**qualified retained second-app users created without measurable source-app trust/utility loss**

Secondary diagnostics: profile visits when available, cross-app CTR, store conversion, install count. None is sufficient alone.

## MintTap / LogMate decision

Current assumption: MintTap and LogMate have materially different specialist audiences. Therefore they remain X1 by default for direct cross-promotion unless live evidence demonstrates a meaningful overlap. Shared publisher identity is useful for provenance; it is not a reason to advertise LogMate inside MintTap or MintTap inside LogMate.
