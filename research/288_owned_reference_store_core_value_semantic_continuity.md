# Research 288 — Owned Reference → Store → Core Value Semantic Continuity

Validated: 2026-09-28

## New finding
For sparse niche apps, an acquisition surface should not be optimized independently. The user-visible promise must remain semantically consistent across the owned/community reference, Store presentation, first in-app destination, and completed specialist job. Conversion lift without that continuity can increase low-quality acquisition.

## GO0–GO8
problem-language evidence → canonical owned answer → Store intent mapping → page eligibility/traffic sufficiency → creative promise parity → destination/deep-link parity → first specialist value → repeated specialist value → KEEP/CHANGE/HOLD/RETIRE

## Platform facts
Apple Custom Product Pages (CPPs) can use different screenshots, previews, promotional text and keywords. Approved CPP keywords can cause the CPP to appear instead of the default product page for those searches. CPPs can also carry a deep link to a specific in-app destination on iOS/iPadOS 18+, and Apple allows up to 70 CPPs. These are capabilities, not a mandate to fragment a sparse audience.

Apple CPP analytics appear only after at least five first-time downloads for the page. Product Page Optimization likewise starts showing results after five attributed first-time downloads; Apple uses Bayesian analysis and labels a treatment better/worse at at least 90% confidence. Apple may label a test likely inconclusive when current traffic is unlikely to reach that confidence within 90 days. Therefore five downloads is a reporting threshold, not evidence that a niche semantic route is validated.

## Sparse-niche operating contract
1. Create a route only for a materially different specialist intent, not a keyword synonym.
2. The owned reference must solve the problem without requiring an install.
3. Store copy/screenshots must preserve the same job and evidence boundary; do not broaden into generic claims to chase conversion.
4. Where platform capability and product architecture permit, route the Store promise to the matching in-app destination. Otherwise make the matching job immediately discoverable after open.
5. Judge the route on first/repeated specialist value as well as Store conversion.
6. If traffic is censored or likely inconclusive, do not multiply variants. Consolidate semantic cohorts or return operator time to community evidence, owned references, onboarding, or product friction.
7. Retire routes whose underlying intent disappears, whose evidence becomes obsolete, or whose Store promise no longer maps cleanly to product capability.

## MintTap application
Candidate semantic routes should be business jobs, not ticker micro-pages:
- understand ROC status/provenance;
- understand portfolio/distribution total-return methodology;
- reconstruct split/reinvestment effects where the product truly supports the job.

A Reddit or search answer about ROC should lead to a provenance reference, then—only when justified—to Store assets that promise the same provenance/portfolio job, and finally to the corresponding MintTap workflow. Do not turn every ticker or monthly distribution into a separate CPP.

## LogMate application
Potential routes should map to pilot jobs such as import/migration continuity or trustworthy logbook record handling, not airline/aircraft keyword proliferation. A migration-focused acquisition promise should land on an onboarding/import path that actually completes migration value; generic Home routing weakens semantic continuity.

## Reusable niche-app rule
Optimize a chain, not a page:
qualified problem intent → truthful owned/community answer → matching Store promise → matching destination → completed specialist value → repeated value.

A channel metric is insufficient if the next semantic handoff breaks.

## Next research
Build a minimum semantic-route audit template for MintTap and LogMate, then inventory only routes for which current product capability and evidence are known. Do not invent traffic, CPP/CSL inventory, or downstream conversion data.
