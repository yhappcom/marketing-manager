# Research 289 — Production Semantic Route Audit Contract

Date: 2026-09-28
Status: Validated

## Core finding
Do not create a new acquisition route merely because a Store platform exposes a routing feature. Create or retain one only when a materially distinct specialist job exists, the Store promise can truthfully represent it, the product has a matching destination/workflow, and traffic/evidence justifies maintaining the segmentation.

## GP0–GP9
GP0 Problem evidence — record independently observed user problem and specialist language. Do not manufacture a problem from keyword tooling alone.

GP1 Source surface — inventory the actual community, owned, social, search, or Store source. Mark absent as NONE and unverified as UNKNOWN.

GP2 Canonical answer — source should be useful before asking for an install. Record authority, provenance, date/state, and uncertainty where material.

GP3 Store route — record the real production default/custom Store route. Never infer that a custom page exists from platform capability.

GP4 Promise parity — compare source problem, Store creative/copy, and expected outcome. Fail the route if Store messaging changes the job merely to improve conversion.

GP5 Destination parity — record the post-install/open destination. A specialist promise that terminates only at generic Home or unrelated onboarding is a DESTINATION GAP.

GP6 First specialist value — define completion of the promised specialist job, not open/session/screen view/ad impression.

GP7 Repeated specialist value — define a meaningful recurrence appropriate to the job; do not force daily retention onto episodic professional utilities.

GP8 Evidence state — use OBSERVED, PLATFORM_ATTRIBUTED, CENSORED, UNKNOWN, or INCREMENTAL_SUPPORTED. Store conversion without downstream specialist value does not justify expansion.

GP9 Decision — KEEP, REPAIR, MERGE, HOLD, RETIRE, or CREATE. CREATE requires distinct-job, destination, maintenance, and evidence gates to pass.

## Minimal ledger
Route ID; app; specialist job; dated problem evidence; source surface; canonical reference; Apple route; Google route; Store promise; product destination; first specialist value; repeated specialist value; evidence state; main gap; decision; re-entry trigger; owner/update date.

## Platform validation
Apple currently supports up to 70 Custom Product Pages with distinct screenshots, previews, promotional text and keywords, unique URLs, keyword-based search routing, and optional deep links to in-app content on iOS/iPadOS 18+. Analytics for a CPP appear after at least five first-time downloads. Operational implication: platform capacity is a routing primitive, not a segmentation target.

## MintTap
Audit real production surfaces before creating ticker-level pages. Candidate jobs remain ROC provenance interpretation, distribution-versus-total-return interpretation, and split/reinvestment reconstruction only if recurring evidence plus matching workflow justify separation. A ticker name alone is not a distinct job. Multiple YieldMax tickers should normally share a route when problem, promise, workflow, and value event are the same.

## LogMate
Before launch, audit route readiness rather than manufacture Store segmentation. Candidate jobs are import/migration continuity, Previous Total continuity, duplicate/reconciliation integrity, and export/record integrity. Airline, aircraft, roster vendor, or jurisdiction should not become separate routes unless they create materially different promises/workflows and have enough evidence to maintain them.

## Reusable niche-app rule
One route equals one materially distinct user job, not one keyword, persona label, ticker, profession subtype, or creative variation.

Before adding a route ask whether the user problem, Store promise, product destination, first-value event, maintenance burden, and learnable evidence are materially different. If most answers are no, merge rather than multiply.
