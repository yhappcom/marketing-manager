# Research 397 — Google Play Search-Keyword Custom Store Listings Are Intent Routing, Not Keyword Stuffing

Validated: 2026-10-03

## Why this matters
Google Play now supports Custom Store Listings (CSLs) targeted to specific Play Search keywords. This creates a zero-paid-media routing surface for niche apps, but it should not be treated as an ASO keyword-stuffing mechanism or as a substitute for Store Listing Experiments.

## Authoritative findings
Google Play permits up to 50 custom store listing pages. A CSL can customize app name, icon, descriptions, and graphic assets. Current audience targeting includes country/region, lifecycle/purchase segments, ads traffic, pre-registration, search keywords, and custom audiences.

For Search keyword targeting, Play Console lets the developer select keywords known to bring traffic or search for additional keywords. A keyword bundle can include spelling corrections and translations, and those variations can be reviewed and selected/deselected.

Store Listing Experiments answer a different question. A default-graphics experiment can test icon, feature graphic, and screenshots; localized experiments can test text and graphics. Results may remain “More data needed,” and experiments auto-stop after six months. Therefore sparse niche traffic should not be fragmented across unnecessary variants.

## Operating conclusion
Search-keyword CSLs are an intent-routing layer:
search evidence → materially distinct specialist intent → truthful CSL → matching first specialist value.

They are not evidence that adding a keyword to listing copy improves ranking, and they do not justify creating a CSL for every query/ticker/aircraft term.

## IR0–IR9 contract
IR0 — Observe real Play Search demand before creating a route.
IR1 — Group query variants that represent the same specialist job.
IR2 — Split only when intent, workflow, evidence, or qualification materially differs.
IR3 — Map every CSL claim to the Claim Registry and current production behavior.
IR4 — Keep screenshots/description semantically continuous with the triggering search intent.
IR5 — Review keyword-bundle spelling/translation variants; do not assume all variants carry identical intent.
IR6 — Preserve default listing as the broad truthful baseline.
IR7 — Measure CSL exposure/install/open evidence with censoring/sparse-data discipline.
IR8 — Use Store Listing Experiments only when traffic can distinguish a business-material effect.
IR9 — KEEP / MERGE / SPLIT / HOLD-SPARSE / RETIRE based on specialist value, not page count.

## MintTap application
Do not create separate CSLs merely for TSLY, CONY, MSTY, NVDY or every YieldMax ticker. Ticker identity alone is not a materially different job.

Potential routes require actual Play Search evidence and production-truth support. Examples worth auditing—not pre-approving—include:
- ROC / distribution provenance;
- split or reinvestment reconstruction;
- portfolio/total-return tracking.

A route should exist only if the query cluster represents a distinct user problem and the listing can truthfully show the corresponding implemented workflow.

## LogMate application
Before launch evidence exists, do not manufacture CSLs for pilot jargon, aircraft types, roster vendors, or import formats. After launch, migration/import, multi-leg logging, Previous Total continuity, export integrity, or offline/PWA workflow may become candidates only if Play Search evidence shows materially distinct intent.

## Reusable niche-app rule
Use query-level routing before cosmetic experimentation when specialist intent is heterogeneous. The unit of Store architecture is the user job, not the keyword.
